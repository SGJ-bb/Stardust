# 方案：LLM 大脑像素小镇游戏（世界书驱动版）

> 面向 **Stradust app 端（Android 主力）** 的一款 2D 像素生活模拟游戏。
> 核心卖点：**世界书即世界**——玩家已有/自定义的世界书(修仙/科幻/中古...)被"编译"成一个主题化、可玩、世界观自洽的活小镇；**镇内每个 NPC 都拥有自己的 LLM 大脑**，具备独立人格、长期记忆、自发社交与对玩家的真实情感。

- 方案日期：2026-09-22（第 2 版，重写为"世界书驱动引擎"架构）
- 状态：规划（待评审确认后进入实施）
- 复用底座：Stradust Android 的 LLM 多厂商接入(`ApiClient`/`ProviderAdapter`)、`WorldInfo` 世界书、`CharacterCard` 人格、长期记忆(RAG)、`GroupChatManager` 群聊多角色、`AffectionManager` 好感度、`VirtualWorldManager` 世界状态、成就、TTS。

## 1. 为什么世界观差异化是"分水岭"

传统游戏内容是**手工设计**的；这里要求**同一套引擎，跑出修仙/科幻/中古截然不同的镇子**。如果让 LLM 在**运行时实时生成一切**(地图/物品/人物/互动规则)，几乎必然得到：前后矛盾、机制失灵、每次打开像抽卡一样随机的"假游戏"，token 成本也会爆炸。

> **核心解法：把架构劈成「编译期」与「运行期」两段。**
> **LLM 负责"提供内容与定义"，引擎负责"保证可玩与自洽"。**

## 2. 总体架构：编译期 → Schema → 运行期

```
玩家世界书(WorldInfo, 自由文本) + 生成地图(用户已有)
        │  [编译阶段] LLM 重活，只做一次，结果缓存
        ▼
   ╔═══════════ 世界 Schema(结构化 JSON, 单点真理源) ═══════════╗
   ║  主题/风格    : 修仙 / 科幻 / 中古 ...                        ║
   ║  地图资源     : 区域类型/生态/可采集物&稀有度                   ║
   ║  物品清单     : 名称/图标/效果/经济模型(参数化)                ║
   ║  NPC 卡组     : 形象描述/人格/日程原型/对话风味                ║
   ║  交互动动词表 : 该世界允许的互动及其"皮肤"                     ║
   ║  全局规则     : 魔法/科技/武学对该世界的加成                   ║
   ║  gameplay_bundle : [扩展位] 预留某世界的专属玩法               ║
   ╚═════════════════════════════════════════════════════════╝
        │  [运行阶段] 引擎只读 Schema；机制恒定为生活模拟
        ▼
   确定性引擎(本地反射层)  +  按需触发的主 LLM(NPC大脑/对话/剧情)
```

**两条铁律：**
1. **机制恒定**：背包/种田/时间/好感度等玩法循环统一且确定性，只是被 Schema"换皮"。
2. **LLM 不实时操控机制**：仅提供内容、定义与情景文案；所有改变世界的动作走白名单校验(见 §4.2)。→ 从根本上杜绝"LLM 生成出坏掉的游戏"。

## 3. 世界 Schema 子系统（逐块化解"复杂"的三块难点）

### 3.1 世界物品
- 物品库**不是手绘**，而是用"生态/经济规则"**参数化生成**。
- 统一骨架：`资源 / 工具 / 食物 / 道具 / 稀有度`。
- 例：修仙 = 灵石/筑基丹/飞剑；科幻 = 能量芯/纳米修复剂/等离子刀；中古 = 铜币/草药/铁剑。
- **图标程序化生成**：基础形状 × 稀有度调色板 × 主题材素质感，无需逐世界手绘。

### 3.2 人物形象
- 把"形象描述文本"映射为**参数化像素生成器**：模板骨架 × 肤色/发型/服饰调色 × 主题配件槽。
- 描述→参数的**确定性映射**：保证同一人物历次打开长相一致（不靠随机）。
- 例：修仙道人(道袍配饰/发髻)、科幻船医(荧光护甲)、中古铁匠(皮甲胡须)。

### 3.3 交互
- 交互动词用一套**固定类别**：`对话 / 赠礼 / 交易 / 委托 / 好感`。
- 每个世界的**皮肤与数值由 Schema 决定**：修仙"交易=交换灵石、切磋=论道"；科幻"委托=接取任务"。
- **每次实时互动的那句"话"** 由该 NPC 的 L3 主 LLM 临场发挥（见 §4）。

### 3.4 地图资源与规则
- 从"生成地图"中提取：区域类型→生态/产出表、采集物稀有度、交通节点。
- 全局规则表：魔法科技武学对"种田/战斗/采集"的加成数值（只影响数值，不改机制）。

## 4. NPC 三层"大脑"

### 4.1 三层脑力模型（成本/延迟与"鲜活"的平衡）

| 层级 | 运行 | 触发 | 成本/延迟 |
|------|------|------|-----------|
| **L1 反射层**（确定性 FSM/Utility） | 本地 60fps | NPC 走动/每日日程/表情/闲逛 | 0 / 0 |
| **L2 轻量层**（本地小模型 / 缓存+人设插值） | 本地/轻量端点 | 擦肩而过路过语等非关键场景 | 极低 |
| **L3 主思维层**（主 LLM，结构化行动） | 云端异步 | 玩家对话/剧情/重要 NPC↔NPC 互动/节日/日切 | 高但按次计 |

**升层原则**：L1 持续跑，遇到"值得思考"的感知事件（玩家靠近、赠礼、言语冒犯、重要关系事件）→ 升级 L3 决策"下一步做什么"，而非只回一句话。
> MVP 阶段可先砍掉 L2，采用"L1 反射 + L3 主 LLM"两段，降首期复杂度。

### 4.2 结构化行动（LLM 不只说话，还要做事且受校验）
复用 `ApiClient.sendChatWithToolLoop()` 的 **tool_call** 机制，LLM 输出受 `GameActionWhitelist` 约束的动作：
```json
{ "speak": "这萝卜种得真好，谢谢你想起我。",
  "actions": [
    { "type": "give_item",  "item": "jade_herb", "to": "player", "affection": +5 },
    { "type": "set_mood",   "value": "happy" },
    { "type": "schedule",   "at": "16:00", "dest": "fountain" }
  ] }
```
- 白名单校验：防越权改状态、防注入、防非法存档。这是"LLM 性格实际改变世界"的落点。

### 4.3 世界呼吸（World Breathing）——后台让小镇"活着"
- 低频调度器（每游戏刻/场景加载/日切触发一次），异步批量把"镇内近况"喂给进驻 NPC，各返回一行状态或一次简短互动。
- 复用 `GroupChatManager` 多角色语义，实现"两居民在广场聊起你刚送的花"的自发社交。
- **频次受上限 + 相关性过滤**：防 token 爆炸与"闹剧感"。

### 4.4 记忆层级（人格连续性）
| 记忆 | 数据 | 复用 |
|------|------|------|
| NPC 个人记忆 | 该 NPC 对玩家/他人/事件 | `MemoryPool`/`MemoryManager`（每 NPC 一份） |
| 小镇共同记忆 | 季节/大事件/关系/流言 | `VirtualWorldManager.WorldState` + `RelationshipGraph` |
| 玩家好感度 | 每 NPC 亲密度 | `AffectionManager` |
| 检索增强 | 回复时取回相关记忆 | `PersonaRagManager`/TF-IDF（轻量降本） |

- 记忆**按需注入**：构造 NPC prompt = 精简人设 + 当前相关世界书条目 + 该 NPC 记忆 topK + 小镇快照。

## 5. 玩法规格（通用循环 + 深度主题）

| 模块 | 内容 | MVP |
|------|------|-----|
| 时间/季节/天气 | 四季节流转，天气影响种田（被世界观换皮） | ✅ |
| 种田/采集 | 耕地/播种/浇水/收获/出售 | ✅ |

| 好感度 | 赠礼/对话/帮忙积累 | ✅ |
| 居民日程 | NPC 按作息在小镇移动（L1） | ✅ |
| 自发社交 | NPC↔NPC 流言/互动（世界呼吸） | ✅ |
| 钓鱼/矿洞/节日 | 扩展 | ⬜ |

## 8. 关键数据流

```
玩家选用世界书(或已有生成地图+世界书)
  → [编译] 后端WorldCompiler: 世界书 → Schema(缓存)；产出物品/NPC/地图资源
  → 引擎加载 Schema → 主题化可玩小镇
玩家与"艾米丽"说话
  → BrainOrchestrator 升层 L3
  → GameLlmService: 人设+相关世界书条目+艾米丽记忆+小镇快照
  → LLM tool_call → 结构化行动 → Whitelist校验 → 逻辑层应用(好感/道具/日程/mood)
  → WorldBreath 记录事件 → 日后其他 NPC 可能转述
  → (可选)TTS
```

## 9. MVP 里程碑（焦点改为"编译流水线跑通"）

| 里程碑 | 目标 | 产出 |
|--------|------|------|

## 10. 成本与延迟优化

- **编译只做一次+缓存**：重活不在运行时反复。
- **合成身份非全量脚本**：NPC prompt 用"人格画像+关系摘要"，不灌全文。
- **预算熔断 CostGuard**：按日/会话 token 上限，触顶自动降级 L1/缓存台词。
- **高频重读回收**：路过语/无意义对话走缓存+人设插值，不触 L3。
- **RAG 轻量化**：TF-IDF 而非昂贵 embedding，命中阈值以上才注入。
- **异步+流式**：LLM 期间 NPC 保持"思考"姿态，回传即现。
- **响应缓存**：相似情境台词缓存，降重复调用。

## 11. 主要风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| **编译质量差**：schema 自洽性不足 | 世界"假"/矛盾 | MVP 强制 3 世界书验收；SchemaValidator+风格一致性校验 |
| token 成本失控 | 财务不可持续 | 分层大脑+熔断+缓存+一次性编译(§10) |
| LLM 延迟破坏"活"感 | 体验断裂 | 异步非阻塞+L1兜底+思考动画 |
| **形象生成不确定** | 同一 NPC 长相漂移 | 描述→参数的**确定性**映射，非随机 |
| 长时间游玩人格漂移/失忆 | 不连贯 | 记忆分级、关系摘要、人设一致性纪要 |
| LLM 不确定 vs 确定性存档 | 存档污染 | 结构性动作白名单 + 存档只存确定性结果与记忆增量 |
| WebView/JS 桥安全 | 注入/越权 | 桥只暴露白名单命令；动作全校验 |
| 离线不可玩 | 体验断裂 | 反射层本地+缓存台词降级 |

## 12. 批判式自评（交付前强制纳入）

> 本方案（第 2 版）在重写时已做批判式自查，重点缺陷仍是：

- **难点的诚实定位**：世界书驱动的真正难点在 **M2/M3 编译质量**，而非画面或单个 NPC——MVP 必须以此为主攻与验收门槛；
- **可能过度设计**：L2 轻量层(§4.1)与 `gameplay_bundle`(§6)本次可先不做，仅预留，避免首期摊子过大；
- **需真实验证而非假设**：schema 自洽性、NPC 对话鲜活度、token 单价，都要在 M2/M5 后用真世界书与内测数据回填；
- **确定性形象映射**是"每次一致"的关键，须作为 M3 硬指标而非可选。

## 记忆与聊天界面同步（用户明确需求，M1 起预留）

> 用户既定目标：**游戏里产生的记忆，后期要与聊天界面的记忆（伴侣对话记忆）同步**，形成"小镇里发生的事，伴侣/后续聊天也能想起来"的连贯体验。

- **结构对齐（关键）**：现有聊天记忆分两类——
  - 结构化场景记忆 `MemoryEntry`（`memory/MemoryPool.kt`）：字段 `content/category/eventTime/place/people/event/scene/details/relationships`，供 RAG 检索；
  - 顶层事实 `MemoryManager.addMemoryFact(content, category)`（`memory/MemoryManager.kt`）。
  游戏内"玩家参与的共同事件记忆"必须**用同一套 `MemoryEntry` 结构 + 同一记忆池**写入，而非另造孤岛，否则同步无从谈起。
- **维度扩展**：`MemoryEntry` 现有字段无"来源"。需为其加**可选的 `source`/`scope` 维度**（如 `game`/`chat`），最小侵入、带默认值，不破坏现有数据。
- **可见性规则**：玩家参与的**共享事件**（对话、赠礼、共同行动）写共享池可被聊天检索到；单个 NPC 的**私密记忆**默认不同步（保护人设连续性，避免把 NPC 内心灌进聊天上下文）。
- **写入时机**：游戏内玩家相关事件落库时**双写**——该 NPC 的 `MemoryUnit` + 共享记忆池（`ContextManager` 的 `globalMemoryPool`）。
- **落地排期**：M1 在 `SaveManager`/`MemoryUnit` 里预留 `source` 字段与双写接口；M5/迭代时真正打通与 `MemoryManager` 的写入与 RAG 命中。

## 美术与资产生态（星露谷级标准，用户明确要求）

> 目标：**整个游戏美术（地图/建筑/角色/道具/UI/环境）对标星露谷的观感**，绝不允许单色平铺或简单方块拼接糊弄用户。

- **风格规范（必须统一）**：色板、描边粗细、明暗层次、像素尺寸、动画节奏——先定规范再大量生产，保证"看起来是同一款游戏"。
- **现状（M0.10 已落地）**：地图由程序化 tilemap 多地貌承载（草/水/田/路/石/花/树，颗粒与明暗），角色为分层高像素 + 行走动画。**已建立资产热替换管线**：地图只认 `drawTile(纹理)` + 一张 tileset，可无痛换入任何更精美的资产。
- **诚实差距**：程序化瓦片有美学上限，距星露谷柔和水彩像素还有一层"专业像素资产供给"未到位（委托美工 / 优质合规素材包 / AIGC 立绘补充）。
- **验收红线（自评守则）**：产出任何画面不得再退回到"单色平铺 / 方块拼接"；地图、角色、环境至少为"多地貌瓦片 + 分层角色 + 明暗"，且持续向专业资产靠近。
- **里程碑**：`M0.10 美术基座`（本版已达成）→ 后续新增 `美术资产接入` 独立里程碑（专业像素资产生态供给 + 全量替换程序化瓦片）。
